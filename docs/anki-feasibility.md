# Anki integration feasibility

**Checked:** 2026-10-09

**Scope:** Source review only. No Anki installation, profile, add-on, browser permission, or integration was accessed or tested.

## Options

| Option                                      | Feasibility                                                                                                                                                                               | Main constraints                                                                                                                                                                                                                          |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hosted HTTPS browser → loopback AnkiConnect | Technically possible in a user-approved browser and supported Anki desktop setup, but not dependable as the default cross-browser product path.                                           | Cross-origin CORS and browser local-network permission must both permit the request. AnkiConnect must be installed/running, trust the exact web origin, and have a compatible API. Browser permission is browser/profile/origin specific. |
| Local companion or reviewed file export     | Preferred. A small local companion can own localhost communication and provide explicit confirmation; a generated text file can be reviewed and imported manually with no network bridge. | A companion needs installation, updates, and a carefully restricted local API. File export is less automatic and requires learner action, but has the clearest preview and recovery path.                                                 |

## Browser-to-loopback findings

An HTTPS page can issue a `fetch()` to an HTTP loopback endpoint only subject to browser policy. Cross-origin `fetch` uses CORS: the service must allow the requesting origin and answer any preflight with the appropriate CORS headers. `no-cors` does not solve this because JavaScript receives an opaque response and cannot inspect the API result ([MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS), [MDN Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch.)).

There is a newer, separate local-network gate. Chrome 142 began prompting for permission for public-web-to-loopback/local requests, with permission limited to secure contexts; Edge 142 is also documented as supporting Local Network Access. The current MDN description uses `loopback-network` and `local-network` permissions and says support varies by browser. It does not establish equivalent support across Firefox, Safari, mobile browsers, embedded webviews, or managed browser configurations. Therefore compatibility must be checked against a named browser/version matrix, and denied/unsupported permission must leave the feature unavailable without degrading core study flows ([Chrome 142 release notes](https://developer.chrome.com/release-notes/142?hl=en), [Chrome Local Network Access announcement](https://developer.chrome.com/blog/local-network-access), [MDN Local Network Access](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Local_network_access)).

The loopback API must stay bound to loopback; it must never be exposed on a LAN/public interface to work around browser policy. Use HTTPS for the hosted origin, standard CORS, a narrow exact-origin allowlist, and the browser's user permission prompt where supported. PNA preflight headers from older proposal examples are not a substitute for current browser local-network permissions. AnkiConnect's documented `requestPermission` action separately asks Anki to trust an otherwise untrusted web origin; it is the first API call recommended by its docs. This is distinct from browser permission and neither grants the other. The canonical source defaults the server to `127.0.0.1:8765` and its CORS origin list to `http://localhost`; a hosted HTTPS origin therefore needs explicit trusted-origin configuration. `requestPermission` can prompt in Anki and persist the exact requesting origin in that list ([pinned AnkiConnect README](https://git.sr.ht/~foosoft/anki-connect/tree/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e/item/README.md), [pinned source revision](https://git.sr.ht/~foosoft/anki-connect/commit/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e), [MDN Local Network Access](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Local_network_access)).

## API, maintenance, profile, and identity limits

The [FooSoft AnkiConnect GitHub repository](https://github.com/FooSoft/anki-connect) is an archived pointer (archived 2025-11-04); the canonical project source is hosted on [SourceHut](https://git.sr.ht/~foosoft/anki-connect). Source review was pinned to master commit `de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e` (dated 2025-12-05); the remotely advertised latest release tag was `25.11.9.0` at `532a3c816e08e91c4367e2799ce3779403d70274`. At the 2026-10-09 check, this is the reviewed canonical upstream, but its latest source commit/release dates to 2025-12-05 and compatibility with current Windows Anki remains untested. The pinned [README](https://git.sr.ht/~foosoft/anki-connect/tree/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e/item/README.md) and [source revision](https://git.sr.ht/~foosoft/anki-connect/commit/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e) document/implement API version 6 actions `requestPermission`, `getProfiles`, `getActiveProfile`, `loadProfile`, `findNotes`, and `addNote`. Any implementation must pin the reviewed revision and validate it against the specific supported Anki versions before relying on those actions.

The pinned implementation of `getActiveProfile` returns Anki's profile-manager name, so it reports a name when this add-on is installed and running. That is not reliable identity binding: a profile name can be changed, the active profile can change between checking and writing, another Anki installation/add-on version may not expose that action, and a returned name does not prove which Langlo learner owns it. Never infer a learner or profile silently. Require the learner to select/confirm the target profile in Langlo, show the returned profile name on every connection/session, require explicit consent before reading or writing, and stop if the profile does not match the learner's explicit choice. Do not invoke `loadProfile` automatically; the API changes profiles ([pinned AnkiConnect README and source](https://git.sr.ht/~foosoft/anki-connect/tree/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e/item/README.md)).

`addNote` normally applies Anki's duplicate check and returns a note ID on success; `findNotes` searches the current collection using Anki query syntax and returns note IDs. These are useful safeguards, not an idempotency guarantee. Duplicate checks are content-based, not an application transaction key; two concurrent attempts can race, and a timeout can leave the caller unable to know whether a write completed. If a reviewed integration is built, include a generated stable Langlo delivery key in a dedicated note field or tag, look it up with `findNotes` before retry, and report ambiguous outcomes for learner review. Do not blindly resend after timeout or enable duplicate creation. Even lookup-before-retry cannot make a check-then-add pair atomic, and edits/deletions or unsupported fields can break future matching ([pinned AnkiConnect README and source](https://git.sr.ht/~foosoft/anki-connect/tree/de6e6e1b8aaf4ae195eb1d1ff6db5409b99b2a3e/item/README.md)).

Anki's text import supports a GUID column for updating existing notes, but its manual says the GUID is intended to be created by Anki. For application-created identity, the manual recommends putting an application ID in the first field; imports can use that field for duplicate checking. This makes an explicit reviewed TSV/text export a viable recovery mechanism, provided the learner confirms note type, field mapping, and target profile in Anki's import UI ([Anki manual: Text Files](https://docs.ankiweb.net/manual/importing/text-files)). Profiles are local desktop collections selected through Anki's profile manager; the manual specifically cautions that profiles are primarily for different people and syncing multiple profiles to one AnkiWeb account can overwrite data ([Anki manual: Profiles](https://docs.ankiweb.net/profiles.html)).

## Recommendation and remaining acceptance

Use a reviewed text export with a stable Langlo application ID in the first field as the first delivery option. It avoids depending on browser-to-localhost policy and lets Anki's own importer preview and apply the changes. If automation later proves necessary, prefer a local companion that communicates with loopback AnkiConnect and presents the exact learner, profile, note changes, and consent locally. Treat direct hosted-browser access as an opt-in experiment for a constrained browser matrix, never as assumed availability.

Before implementation acceptance, pin and review the chosen AnkiConnect source/release and Anki version range; specify companion installation/update and local API threat boundaries; define learner-to-profile selection and reconfirmation behavior; test browser permissions, CORS, API errors, profile switching, duplicate/timeout recovery, and import review using disposable synthetic data. These are pending engineering acceptance items. This source review does not prove any live integration, supported Windows Anki behavior, or successful write to a learner collection.
