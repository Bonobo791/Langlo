# T008: safe runtime configuration and errors

Date: 2026-10-06. Plan marker: language-app-adm-20261006 / T008. Verified for the current foundation behavior; auth/providers remain absent.

## Contracts and test-first evidence

Before implementation, native Node assertions observed Not implemented failures for safe default config, diagnostic field projection, safe error and strict property controls. After runner setup was corrected to Kit 3, the real Vitest tests observed 17 failing behavior cases, then all 17 passed. A shrunk exact-host regression later expanded the config coverage.

The parser disables data by default, validates explicit deployment/origin/flag/revision values, accepts only isolated fixture file config locally, and requires complete explicit remote production config without connecting to it. Invalid values throw only fixed variable-name messages. Explicit private dynamic env definitions and server-only config never enter page data.

Hooks ignore incoming correlation headers and assign a fresh UUID. Safe diagnostics contain only operation, category and correlationId, excluding arbitrary error payloads, stacks, answer text, cookies, URLs and secrets. Error pages use fixed prose and a safe request reference. Liveness bypasses application configuration; readiness truthfully returns foundation-in-progress 503.

## Built-server observations

- Private GET /app/cards returns 303 /login with private,no-store and noindex/nofollow; private POST returns safe 503 without reflecting a synthetic answer
- /health/live returns 200/live and unique server UUIDs; supplied correlation text is ignored
- /health/ready returns 503/foundation-in-progress, while /build.json returns unknown/local-foundation unless a validated revision is explicitly configured
- A second built server with an invalid synthetic DATA_ENABLED value returns fixed configuration-unavailable 503; liveness still returns 200. Body/logs exclude the invalid value, variable name, submitted answer and stacks
- The slash-variant private-header regression first failed for /login/. Root trailingSlash:ignore plus normalized hook classification fixed /login/, /recover/, /reset/ and /app/cards/; both project HTTP tests then passed
- Build with a synthetic private token produced no client-file sentinel leaks
- Independent review found no synthetic query/path token in raw built HTML or private configuration in client assets
