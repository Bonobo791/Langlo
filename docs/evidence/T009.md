# T009: isolated schema and migrations

Date: 2026-10-06. Marker: `language-app-adm-20261006 / T009`. Scope: local disposable foundation only. Reviewer disposition: independent review findings corrected with observed regression tests; final owner acceptance remains separate. No remote publication.

## Implemented deliverable

- Twelve real SQLite tables exported from server-only Drizzle `schema.ts`, with owner-aware composite foreign keys, exact question/content-version relations, independent/assisted attempt kinds and owner/submission idempotency
- Three checked-in SQL migrations plus generated snapshots/journal: initial owned study history, immutable canonical card identities and owner-bound delivery records, then strict numeric/update-identity hardening
- Stable tuple-framed SHA-256 SourceID helper and database uniqueness; editable fields/format and retry metadata do not enter the identity
- Approval-at-insertion trigger, immutable canonical identity trigger, claim lease and acknowledgement shape checks
- Explicit local-only connection/migration helpers; lightweight path/link guard; guarded fixture create/seed/reset/dispose CLI and synthetic fixtures
- Detailed fields, nullability, ownership, source/retention assumptions, migration/rollback limits and remaining work in `docs/schema.md`

## Generated invariant and concrete fault

DB-01's independent rule is that learner B cannot attach a session to learner A's enrollment, regardless of generated session identifier or valid mode. The actual libSQL property uses 100 bounded generated cases by default, fresh migrated/seeding state inside every run, snapshots before/after and the strict shared seed/path/run controls. Synthetic IDs include arbitrary strings; valid modes are practice/assessment/mixed-review. The oracle is the ownership requirement and unchanged persisted snapshots, not a result calculated by production code. No property failure/shrink was observed on the correct implementation.

`node tests/fixtures/ownership-fault.ts` is a reproducible deliberate fault experiment. It clones the migrations into a separate temporary directory, deletes the actual enrollment/owner/language FK from that copy, migrates another marked disposable DB and tests the same foreign-owner relation. The observed result is exit 1: `Missing expected rejection: ownership invariant must detect deleted composite FK`. Cleanup runs in `finally`; checked-in migrations are never modified. The deterministic regression is learner-b → enrollment-a. This is concrete constraint-fault evidence, not a Stryker score or a claim that the property suite killed a mutation.

## Actual separate-process concurrency acceptance

Independent review correctly distinguished independent connections from actual concurrent contenders: Promise.all over a synchronous local libSQL driver in one JavaScript thread is insufficient process-contention evidence. `tests/db-concurrency.test.ts` and `tests/fixtures/concurrent-writer.ts` replace that claim with a real separate-process readiness/release barrier using stdin/stdout only. No IPC sockets are used.

Test-first observation: with a no-insert writer scaffold, `npm test -- tests/db-concurrency.test.ts -t 'separate ready/released'` exited 1 on the intended assertion `concurrent duplicate writers must persist one owner-A identity`, with observed `0 !== 1`. The actual INSERT was implemented afterward.

Positive run:

- Three independent Node child processes propose different IDs for the same learner-a/language/skill/canonical mistake/SourceID; a fourth independently proposes learner-b's otherwise identical mistake
- Every child opens its own connection to the same explicitly guarded file-backed fixture and reports its PID and readiness before awaiting its stdin release
- The test asserts all four PIDs are distinct and different from the test process PID, and that no card rows exist while the writers are waiting at the barrier
- Only after all writers are ready does it release them to issue the conflicting SQL INSERTs. All child processes must report their insert effect and exit successfully
- Persisted results contain exactly one learner-a canonical identity and its stable SourceID, plus exactly one learner-b identity with a distinct SourceID. Learner-a's total insert effects equal one

Negative/fault run: a separate temporary copy of the versioned migrations replaces exactly the canonical-identity and SourceID UNIQUE-index DDL with `SELECT 1` no-ops, then migrates another guarded fixture. Two ready/released learner-a processes persist two identical canonical/SourceID rows under different proposed IDs; total insert effects are two. The very same single-identity assertion throws `concurrent duplicate writers must persist one owner-A identity`, and the fault test requires that detection. The first fault-copy attempt produced an empty SQL statement after literal DDL removal, which libSQL rejected; using explicit no-ops preserves executable migration statement boundaries without restoring uniqueness.

`npm test -- tests/db-concurrency.test.ts` passed 1 file / 2 tests in 4.12s. `npm run check` reported 0 errors/0 warnings after introducing the process harness; scoped ESLint passed. Startup is bounded to 10 seconds per child; insertion and exit are bounded to 5 seconds after release. Cleanup kills any unfinished writers and waits for their close notifications before disposing the database. This establishes actual separately scheduled process contenders and database uniqueness under this controlled release, not exhaustive operating-system schedule coverage.

The deterministic regression is three competing learner-a proposed IDs plus one learner-b ID; the deliberate fault uses two learner-a proposed IDs. No random shrink or generated property mutation-kill claim is made for these two process tests. Checked-in schemas/migrations, package configuration and existing delivery/constraint tests were untouched by this concurrency follow-up.

Post-concurrency checkpoint: npm test passed 11 files / 59 tests in 21.60s with the hardening regressions included. A subsequent heavily concurrent verification run exposed a bounded seed-process cold-start failure; the final verification record supersedes this checkpoint and records the minimal driver-only seed fix and final results. Scoped lint/format checks also passed.

## SQL-only fixture startup regression and bounded diagnostics

A later verification run under simultaneous type-check/build activity failed the CLI lifecycle at 12,433ms while a seed subprocess exceeded its existing 5-second bound; 58 of 59 tests passed in that run. The earlier 59-test checkpoint therefore did not establish reliable cold-start behavior. The available failure log contained the failed seed command but no serialized exit/signal details, so it could not independently distinguish an SQL rejection from a timeout.

Cold subprocess measurements separated initialization from actual database work:

| Probe                                            | Wall time | Module import | Database operation |
| ------------------------------------------------ | --------- | ------------- | ------------------ |
| Empty Node process                               | 89ms      | n/a           | n/a                |
| SQLite-only driver import                        | 106ms     | 17ms          | n/a                |
| Full connection/Drizzle/schema import and SELECT | 2,530ms   | 2,102ms       | 29ms               |
| Old seed path                                    | 808ms     | 685ms         | 10ms               |
| Driver-only seed after fix                       | 217ms     | 78ms          | 18ms               |

These are diagnostic samples, not universal performance guarantees. They show that initialization dominated the SQL-only seed path. The seed fixture uses raw SQL and has no need for Drizzle table initialization.

`openFixtureClient` now provides the same explicit target validation, SQLite-only transport, enabled foreign keys, busy timeout and close-on-error behavior without importing the ORM/schema graph. `openFixtureDatabase` loads Drizzle and the schema lazily only for operations that require them. The SQL-only seed and independent concurrent-writer fixtures use the minimal client seam. No schema, migration or package changes were needed.

A retained regression starts a real seed subprocess with a Node module-loader hook that rejects any Drizzle or full-schema import. Before the change it failed in 212ms because seed still imported that graph. After the change it seeded actual local rows and verified foreign-key integrity while the hook remained enabled. This structural check prevents the costly dependency path from returning, rather than relying only on a wall-time threshold. Node's synchronous module-loader hook is documented in the [official module API](https://nodejs.org/api/module.html#moduleregisterhooksoptions) and was exercised on the pinned Node 24 runtime.

`runFixtureCli` wraps test subprocess failures with bounded, safe diagnostics: elapsed milliseconds, numeric/allowlisted error code, killed flag, signal and only the fixed known CLI error text. It does not retain the raw execFile message/cause, supplied targets, arbitrary child output or ambient environment. A deterministic 50ms timeout probe observed `killed: true` and `SIGTERM`, while assertions excluded fixture paths/URLs and a synthetic ambient secret from the error message. Command failures remain distinguishable from timeout kills without exposing their arguments.

The seven-action CLI lifecycle completed in 4,187ms; the no-ORM seed regression completed in 547ms; the timeout diagnostic regression completed in 84ms. The actual separate-process duplicate/fault tests remained green. `npm run check` reported 0 errors/0 warnings; scoped ESLint and Prettier checks passed.
