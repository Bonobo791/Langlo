### Native persistence and scheduling

Added owner-scoped deck, note, generated-card, and append-only review-event tables in migration `0004_material_sway.sql`. The service uses the real `ts-fsrs@5.4.2` scheduler and stores its state, due instant, revision, version, and parameters. Review time is assigned by the server within the write transaction; the browser/test caller supplies a rating, expected revision, and stable submission ID. Tests create and approve notes, close and reopen a separate synthetic session context, then review and retrieve updated Basic and Cloze state. They exercise:

- same-owner retrieval and other-owner `NOT_FOUND` behavior;
- draft review rejection and explicit approval;
- Basic and restricted Cloze review submissions, with persisted state read from a fresh test database session;
- real FSRS review state update, revision increment, persisted due date, exact duplicate retry, and conflicting idempotency-key rejection;
- stale revision rejection, including two distinct concurrent submissions against the same revision (one is applied, lock contention is retried, and the other is rejected stale);
- cross-owner review denial with unchanged owner data and unchanged grammar evidence;
- single-group Cloze accepted and unsupported `c2` rejected;
- direct review-history deletion, update, and replacement blocked, while owner/card deletion after a review cascades to the event row for intentional learner-data erasure;
- per-card persisted FSRS parameters used for scheduling and review events, with unsupported scheduler versions and malformed parameters rejected without changing card state;
- discriminated Basic/Cloze content validation, nonblank text limits of 4,096 characters, empty submission-ID rejection, and stable errors for malformed card-state JSON;
- review-event composite primary key used without a duplicate unique index or hidden rowid, with migration-0004 table option/triggers called out for future rebuilds.

These are test-fixture session identities only. Production authentication and browser session middleware do not exist in this spike. Review history rejects application edits and direct SQL UPDATE/DELETE/REPLACE; deleting the owning card, note, deck, or account intentionally erases its dependent history by cascade. Restore validation is documented as a future operational requirement and was not run.

### Review findings — 2026-10-10

- **Unicode code-point limit — valid and fixed.** JavaScript's `String.length` counted supplementary-plane characters as two UTF-16 code units, while the SQLite `length()` constraint counts them as one Unicode code point. The validator now iterates code points and stops at the first value beyond 4096, avoiding a temporary array for oversized input. A regression test checks exact-limit and over-limit Basic and Cloze content. The test was observed failing before the validator change and passed afterward.
- **Trigger identifier quoting — valid and fixed.** The three review-history triggers now use double-quoted SQLite identifiers consistently, including `OLD` and `NEW` references. The migration tests passed.
- **Regex alternation — valid and fixed.** Equivalent `m|h|d` alternations now use `[mhd]` in both scheduler-step validators.
- **Await inside the retry loop — retained intentionally.** Each SQLite write attempt must finish with `SQLITE_BUSY` before the bounded backoff and next attempt; parallelizing retries could overlap writes. The warning is a static-analysis false positive for this serial retry loop.
- **Repeated JSON type literal in the migration — retained intentionally.** SQLite `CHECK` constraints cannot share a local constant, and removing a repeated type check would weaken direct database validation. A migration comment records why the repetition remains; this finding cannot be safely fixed as a constant extraction.

## Later manual Windows integration procedure

This procedure is pending explicit owner approval before any desktop, profile, add-on, or real-collection access. Use a new disposable Windows Anki profile and synthetic note only; never use either learner's actual profile for the acceptance run.

1. Record the Windows Anki version, browser name/version, and reviewed AnkiConnect release/commit. Install the reviewed add-on only after approval. Confirm its listener binds to `127.0.0.1` and is not reachable on a LAN/public interface. Do not expose a port or add wildcard origins.
2. Open the intended HTTPS Langlo origin. Have the owner explicitly approve the exact origin in AnkiConnect and the browser's local-network permission prompt. If either permission is unsupported or denied, confirm Langlo reports unavailable and sends no note.
3. Select the synthetic learner and the named disposable profile explicitly. Compare the active Anki profile name to the selected target and stop on any mismatch; do not call `loadProfile` automatically.
4. Approve a single synthetic note, send it once, and record the resulting note identity/Anki note ID without capturing private collection contents.
5. Retry the same synthetic delivery. Verify lookup finds the same identity and note ID and that no second copy is created.
6. With only the disposable profile, test Anki closed/unavailable, denied browser permission, denied AnkiConnect origin permission, wrong active profile, malformed API response, and a delayed/lost response after a potentially successful add. Confirm each case fails closed; for the uncertain add, look up the stable identity before any retry and do not blindly add again.
7. Remove only the synthetic note/profile after review and record exact versions, commands/actions, observed results, and reviewer disposition. Do not alter firewall/browser network settings to make the test pass.
